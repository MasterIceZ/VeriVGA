# M0 spike: worker compile and first frame in a webview (Task 3)

Date: 2026-10-14. Machine: Apple M2 Pro, macOS 26.5.1, Node 24.19.
Hosts: VS Code 1.141.1 desktop (via `@vscode/test-electron`) and VS Code web 1.142.0-insider
in headless Chromium (Playwright 1.64, via `@vscode/test-web`). Design: `examples/stripes`.

## Outcome

The planned architecture works as designed in both hosts. **No fallback was needed.**

| Risk (requirements §7, brief Step 7) | Result |
|---|---|
| Web Worker inside a webview | Works on desktop and web. The worker script is fetched from its webview URI and started from a Blob URL (`worker-src blob:`). Verilator runs inside the worker. |
| Posting a `WebAssembly.Module` to the worker | Works in both. The Module is compiled once on the main thread and posted to the worker in an `init` message. Each compile instantiates it through Emscripten's `instantiateWasm` hook. |
| binaryen top-level await in the bundle | Works. `dist/webview.js` is ESM (target `es2022`, which already allows top-level await; `esnext` isn't needed) and is loaded with `<script type="module">`. |
| CSP | The policy in `webviewHtml.ts` is enough. `'wasm-unsafe-eval'` covers Verilator's and binaryen's WASM, and binaryen decodes its embedded WASM with `atob` (no `fetch`), so `connect-src` doesn't need `data:`. No CSP violations were logged. |

The frame drawn in the browser matches Node byte for byte. A temporary hash of the webview's
pixel buffer (web run) equalled a Node render using the same sequence (`1396722794`). It
differs from `test/golden/stripes.png` only because the golden test also calls
`skipToFrameBoundary`, which the skeleton (like upstream's app) doesn't.

## Build findings

- Both Emscripten builds `require`/`import` Node-only modules inside their
  `ENVIRONMENT_IS_NODE` branch: Verilator uses `fs`, `path` and `child_process` (plus
  `crypto` inside a `try`, which esbuild tolerates), and binaryen uses `await import("module")`.
  The webview and worker bundles mark them external (`emscriptenNodeOnly` in `esbuild.mjs`).
  They are never reached in a browser.
- `parseVerilatorXml` lives in `compile.ts`, so importing it pulls `verilator_bin.js` (the
  270 KB Emscripten loader; its factory is never called there) into `webview.js`. That's
  harmless next to binaryen's 8.2 MB.
- macOS caps Unix socket paths at 103 characters. VS Code puts its IPC socket in the user
  data dir, and the default `.vscode-test/user-data` is too long in this worktree.
  `.vscode-test.mjs` passes a short per-checkout `--user-data-dir` in the OS temp dir.

## Findings for later tasks

- **Location-less Verilator errors are lost in the browser (Tasks 10–12).** Emscripten's
  `callMain` swallows the `ExitStatus` thrown on a failed run, so the browser relies on
  `ErrorParser`. That parser only matches `%Error: file:line:col: …`, so errors such as
  `%Error: Specified --top-module 'nope' was not found in design.` are dropped. The result
  is then just `XML parsing failed: Error: No such file or directory`. Seen by temporarily
  sending `topModule: 'nope'`. Upstream behaves the same. Since a wrong `verivga.topModule`
  setting would hit this, consider an `ErrorParser` fallback for `%Error: <message>` lines
  (an upstream-file edit to log in `UPSTREAM.md`).
- **The failure path settles.** The bad-top-module run above returned `ok: false` promptly;
  the worker didn't hang. Task 2's `instantiateWasm` gap (no `.catch`) didn't show up.
- **test-web downloads VS Code Insiders by default.** The `test:web` command from the brief
  has no `--quality`, so the web run uses 1.142.0-insider. Add `--quality=stable` if web
  results should track vscode.dev stable.
